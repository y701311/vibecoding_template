# Project Type: Data Engineering

Ingestion / Transformation / ETL・ELT / Pipeline / Job / Gold dataset

Data Engineering は繰り返し動く。
一度うまく動くことより、**失敗しても壊れないこと**が成果物の条件になる。

---

## 確認すべき観点

### 再投入したらどうなるか

最重要。ここを聞かずに実装してはならない。

> 同じデータをもう一度取り込んだ場合、置き換えたいですか、追加したいですか？
> 二重に数えられると困りますか？

→ 置き換えなら MERGE / overwrite by partition。追加なら append。
　 技術方式は聞かない。**業務としてどちらが正しいか**だけ聞く。

### 何が「同じ行」か

> このデータで、同じものを指していると判断できる項目は何ですか？
> （注文番号、日付＋店舗、など）

重複排除もマージもここで決まる。既存テーブルの主キーがあればそれを使う。

### 遅れて届くデータ

> 過去の日付のデータが後から届くことはありますか？
> あった場合、過去の集計も直す必要がありますか？

ある → 単純な append では合わなくなる。再計算範囲を決める。

### 値が変わる履歴

> マスタの値が後から変わったとき、当時の値も確認できる必要がありますか？

必要 → 履歴を持つ設計。不要 → 上書きでよい。

### 実行タイミングと量

> どのくらいの頻度で更新されれば十分ですか？
> 1 回あたりどのくらいの量が来ますか？

日次で足りるなら Streaming にしない。

### 失敗したときの扱い

> 取り込みが失敗したとき、誰がどう気づけばよいですか？
> 途中まで処理された状態が残っても大丈夫ですか？

### データ品質

> 必須項目が空だったり、想定外の値が入っていたらどうしますか？
> （止める / その行だけ除いて記録する / そのまま通す）

黙って通すのが一番危ない。**どれを選ぶかは業務判断**なので聞く。

## Databricks での作り方

| やること | 使うもの |
|---|---|
| 継続的な取り込み・変換 | Lakeflow Pipelines |
| 定期実行・依存関係 | Lakeflow Jobs |
| ファイルの増分取り込み | Auto Loader |
| テーブル・権限 | Unity Catalog |
| デプロイ | Databricks Asset Bundles |

- リトライ・スケジュール・依存関係を Python で自作しない。Jobs にある。
- 品質チェックを自作フレームワークにしない。Pipelines の expectations を使う。
- Bundle は本番デプロイが必要になってから作る。開発中は不要。

### Medallion

品質境界・責務分離・再処理境界として有効なら使う。
**単純な案件で 3 層に分けることを目的化しない。**

- Bronze: 生データをそのまま。加工しない（後から再処理できる保険）
- Silver: 型・重複・品質を整えた状態
- Gold: 業務が読む形

ファイル 1 本を集計するだけなら Bronze / Gold の 2 層でも、1 層でもよい。

## Idempotency

「同じ入力を 2 回処理しても結果が変わらない」を必ず設計に入れる。

| やり方 | 使いどころ |
|---|---|
| MERGE（キーで upsert） | 更新も来る、キーがはっきりしている |
| パーティション単位の上書き | 日次バッチ、その日の分をまるごと入れ替える |
| Auto Loader | ファイル取り込み、処理済みファイルを自動で除外 |
| append のみ | 追記が正しい業務（ログなど）で、重複が来ない保証があるとき |

素の `INSERT` を再実行安全と思ってはならない。

---

## 落とし穴

- 開発中の小さいデータでしか試さず、本番量で初めて落ちる
- 失敗したときに中途半端なデータが残り、再実行すると二重になる
- 上流のスキーマ変更に気づかず、黙って NULL が入り続ける
- 全件洗い替えで済むものに複雑な増分処理を組む（逆もある）
- タイムゾーン。UTC / JST の取り違えは日次集計を丸ごとずらす

---

## 典型的な検証

- **同じ処理を 2 回連続で実行し、件数と集計値が変わらないこと**
- 途中で失敗させてから再実行し、正しい状態に戻ること
- 過去分の再処理（backfill）を 1 期間分試す
- 入力件数と出力件数の突き合わせ（落ちた行の理由を説明できるか）
- 想定外データ（NULL、重複、型違い）を 1 件混ぜて挙動を確認する
- 日付の境界（月初・月末・年跨ぎ）

## DoD 追加項目

- Idempotent であることを**実際に 2 回実行して**確認した
- 失敗が検知できる（Job のアラート等）
- 復旧手順が決まっている（どこからやり直すか）
- 監視対象が決まっている
- 入力と出力の件数差が説明できる
