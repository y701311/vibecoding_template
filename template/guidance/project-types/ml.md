# Project Type: Machine Learning

Forecast / Classification / Regression / 異常検知 / 特徴量 / 学習 / 推論

ML は「動いた」と「使える」の距離が一番遠い。
精度の数字が出たことは成果ではない。
**その数字が本番でも再現するか**が成果物の条件になる。

---

## まず確認すること

### そもそも ML が要るか

- 前年同月・直近の平均・単純なルールで足りないか
- 予測ではなく、集計や可視化で判断できないか
- 学習に使える実績がどれだけあるか（数ヶ月分では季節性が取れない）

**単純な方法で足りるなら、それが正解。**
ML にすると、精度検証・再学習・劣化監視が永続的な運用コストとして乗り続ける。

判断に迷うなら、まず Baseline（前年同月や移動平均）だけ作って利用者に見せる。
それで足りるなら ML は要らない。足りないなら、そこが出発点になる。

---

## 確認すべき観点

### 予測結果を使って何をするのか

> この予測が出たら、誰が何をしますか？

発注量を決めるのか、人員を配置するのか、アラートを出すのか。
用途が決まると、必要な精度も、外したときのコストも決まる。

### 外したときにどちらが困るか

> 多めに予測して外れるのと、少なめに予測して外れるのでは、
> どちらのほうが困りますか？

在庫なら過小予測（欠品）が痛い、廃棄なら過大予測が痛い。
これで評価指標が変わる。**利用者は「精度」としか言わないので、こちらから聞く。**

### 今はどうやっているか

> 今は何を見て決めていますか？

必ず聞く。これが Baseline になる。
「去年の同月の実績」「担当者の勘」でも Baseline として比較対象にする。

**Baseline に勝てていないモデルを、勝ったかのように報告しない。**
勝てなかった場合は、そのまま本番へ進めず、事実を示して利用者の判断を仰ぐ。

### いつ時点の情報が使えるか

> 予測する時点で、どの情報まで手元にありますか？

Leakage を防ぐ最重要の質問。
学習データにあるからといって、予測時点で入手できるとは限らない。

### どのくらい先を、どの単位で

> どのくらい先まで予測が必要ですか？
> 店舗ごとですか、商品ごとですか、その組み合わせですか？

粒度が細かいほどデータは薄くなる。データ量と合っているか確認する。

### いつ使うのか

> 一度だけ精度を見たいのか、これから毎回動かしたいのか。

前者なら Standard。後者は Production 昇格の対象になる。

## Databricks での作り方

| やること | 使うもの |
|---|---|
| 実験記録・指標・パラメータ | MLflow Tracking |
| モデルの登録・バージョン | Unity Catalog のモデル |
| 学習・推論の定期実行 | Lakeflow Jobs |
| 特徴量の共有 | 必要になってから。最初は普通のテーブルでよい |
| 探索 | Notebook（`notebooks/exploration/`） |

- 指標の記録を自作の CSV / ログにしない。MLflow がある。
- 独自の学習フレームワークを作らない。
- Feature Store は「複数モデルで同じ特徴量を共有する」必要が出てから。

---

## Leakage

ML で最も多く、最も気づきにくい事故。
精度が異常に良いときは、まず Leakage を疑う。

チェックすること。

- **時間**: 予測対象の時点より後の情報が特徴量に入っていないか
- **集計**: 全期間で作った平均・合計を特徴量にしていないか
  （学習データの範囲だけで作る）
- **目的変数由来**: 実績が確定してから初めて埋まる列を使っていないか
  （例: 「キャンセルフラグ」で売上を予測する）
- **分割**: 時系列なのにランダム分割していないか
- **重複**: 同じ実体が学習側と評価側の両方に入っていないか

---

## 評価

- 時系列は**時間で分割する**。ランダム分割は使わない。
- 予測して実績と比べる（backtest）を、複数の期間で行う。
  1 期間だけ良いのは偶然のことがある。
- Baseline と同じ条件・同じ期間・同じ指標で比較する。
- 指標は用途に合わせる。
  MAE / RMSE / MAPE は外れ方の性質が違う。分類なら不均衡を考慮する。
- **全体の平均だけ見ない。** 主要な店舗・商品ごとに外れ方を見る。
  平均は良いのに主力商品で大きく外していることがある。

---

## 落とし穴

- Baseline を用意せずに「精度 90%」と報告する
- 学習データの期間に特殊事情（コロナ、キャンペーン）があるまま一般化する
- 予測できないもの（新規商品、新店舗）の扱いを決めていない
- 予測値が負になる、在庫を超える等、業務上ありえない値をそのまま出す
- 再学習の頻度を決めずに本番投入する

---

## 典型的な検証

- Baseline との比較（同一期間・同一指標）を表で示す
- backtest を複数期間で実行する
- Leakage チェックの結果を明示する（上のリストを 1 つずつ）
- 学習データと予測対象の分布がずれていないか確認する
- 予測値が業務上ありえる範囲に収まっているか
- データが足りない対象（新規・少数）で何が起きるか確認する

---

## DoD 追加項目

- Baseline との比較を実施し、結果を報告した
- 評価用の分割が用途に対して適切（時系列なら時間分割）
- Leakage チェックを実施し、確認した項目を明示した
- 指標を報告した（全体と、主要セグメント別）
- 予測できないケースの扱いが決まっている

本番投入する場合は `guidance/templates/production-readiness.md` も読む。
再学習の頻度と、精度が劣化したときにどう気づくかを決める。
