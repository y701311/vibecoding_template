# Project Type: Analytics

SQL 分析 / Excel 処理 / Dashboard / Notebook 分析 / レポート / EDA

Analytics は「人が読んで判断するもの」を作る。
正しく動くことに加えて、**数字の意味が説明できること**が成果物の条件になる。

---

## 確認すべき観点

推測できるものは推測する。残ったものだけ、業務の言葉で聞く。

### 誰が何を判断するのか

一番重要。ここが曖昧だと、正しいが使われない集計ができる。

> この数字を見て、どういう判断をしますか？

### 集計の定義

「売上」「稼働率」「アクティブユーザー」は、社内でも定義が割れやすい。

> 売上はキャンセル分を引いた後の金額ですか？
> 税込ですか、税抜ですか？

既存の Dashboard やレポートに定義があるなら、**まずそれに合わせる**。
勝手に別定義を作ると数字が合わないという問い合わせを生む。

### 期間と粒度

> 月次ですか、日次ですか？
> 月初〜月末で締めますか、それとも別の締め日がありますか？

### 更新のタイミング

> いつ時点のデータが見られれば十分ですか？（前日まで / リアルタイム）

一度きりの分析なのか、繰り返し見るものなのかで作りが変わる。
繰り返すなら Data Engineering が Supporting に入る。

### 対象範囲と除外

> テスト用のデータや社内取引は除きますか？
> 退職者・閉店した店舗はどう扱いますか？

### 数字が合わないときに何を見るか

> 集計結果がおかしいと思ったとき、元の明細まで遡れる必要がありますか？

## Databricks での作り方

| やること | 使うもの |
|---|---|
| 探索 | Notebook（`notebooks/exploration/`） |
| 定型集計 | SQL / View、繰り返すならテーブル化 |
| 可視化 | AI/BI Dashboard |
| 定期実行 | Lakeflow Jobs |
| データの置き場 | Unity Catalog |

- 探索の Notebook をそのまま定期実行の本体にしない。
  繰り返し使うと決まった時点で SQL / View / Job へ切り出す。
- Excel の読み込みは一度テーブル化してから集計する。
  Excel を毎回読み直す集計はデバッグできない。
- Dashboard を作る前に、元になる集計結果を**テーブルか View として確定させる**。
  Dashboard の中にロジックを埋めると再利用も検証もできない。

## Excel 処理の注意

Analytics で最も事故が多い。

- **再投入**: 同じ月のファイルをもう一度取り込んだらどうなるか。
  置き換えか追加かを必ず確認する（→ 二重計上）。
- **列名の揺れ**: 月によって列名や列順が変わる前提で読む。
  想定と違う場合は落とす。黙って NULL で通さない。
- **結合キー**: 店舗名・商品名などの文字列結合は表記揺れで落ちる。
  マッチしなかった行の件数を必ず出す。
- **型**: 数値に見えて文字列、日付に見えて連番、が普通に混ざる。

---

## 落とし穴

- 合計だけ見て、**マッチしなかった行・NULL・重複を見ない**
- 元データの母数を確認せずに比率を出す
- 「先月比」の先月の定義（暦月 / 直近 30 日）が曖昧なまま実装する
- Notebook のセル実行順に依存した結果を「動いた」とする

---

## 典型的な検証

- 全体の合計が元データの合計と一致するか（件数と金額の両方）
- 結合で落ちた行数、NULL の件数、重複の件数を出す
- 既存のレポートや Dashboard がある場合、**同じ期間で数字を突き合わせる**
- 期間の境界（月初・月末）が意図どおりに含まれているか
- 上から順に一度通し実行して、同じ結果になるか
