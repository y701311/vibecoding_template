# Preset: rag

社内資料を検索して、その内容に基づいて答える仕組み

`guidance/project-types/ai-application.md` の**差分**。先にそちらを読むこと。
ここには RAG に固有のことだけ書く。

---

## 推奨 Type

- Primary: AI Application
- Supporting: Data Engineering（資料の取り込みと更新）

**作業量の大半は Data Engineering 側にある。**
資料が PDF や Word で散在している場合、取り込みと整形が本体になる。
最初にそのことを利用者へ伝える。

---

## まず確認すること

### そもそも RAG が要るか

- 資料が数十ページしかない → 全文をそのまま渡せば足りることがある
- 答えが構造化データにある → SQL で答えるほうが正確
- 一括で分類・要約したいだけ → AI Functions で足りる

**検索が本当に必要か確認してから作る。**

---

## 追加で確認する観点

### どの資料が正か

> 同じ内容の資料が複数ありますか？古い版は残っていますか？

RAG の事故の大半はここ。**古い版と新しい版を両方取り込むと、古い答えを返す。**
取り込む対象を最初に決め、決めた範囲を `docs/project.md` に書く。

### 資料の更新

> 資料が更新されたら、どのくらいで反映されるべきですか？
> 削除された資料はどうしますか？

更新の反映を決めないと、時間とともに嘘をつくようになる。
削除の反映も忘れられやすい。

### 見せてよい範囲

> 人によって見せてよい資料が違いますか？

違う → **検索の時点で絞る。** 回答時にフィルタしても、モデルは既に読んでいる。

### 資料の形式

> 資料は何で書かれていますか？（PDF / Word / Excel / Confluence / スプレッドシート）
> 表や画像に重要な情報が入っていますか？

表と画像はテキスト抽出で落ちる。落ちるなら、そのことを利用者に伝える。

### 答えられるべき質問

> どんな質問に答えられれば「使える」と言えますか？

具体例を 5〜10 件もらう。これが評価データの土台になる。
**もらえないなら、資料から自分で作って確認してもらう。**

### 答えられなくてよい質問

> 逆に、この仕組みが答えなくてよいことは何ですか？

範囲外の質問に「分かりません」と返せることを成功条件に入れる。

## Databricks での作り方

| やること | 使うもの |
|---|---|
| 資料の取り込み・更新 | Lakeflow Jobs / Pipelines |
| ベクトル検索 | Mosaic AI Vector Search |
| 生成 | Foundation Model API / Model Serving |
| 権限による絞り込み | Unity Catalog |
| トレース・評価 | MLflow Tracing / Evaluation |

独自のベクトル DB を立てない。埋め込みの管理を自作しない。

---

## 品質が出ないとき

**検索から疑う。生成側のプロンプトを先に直さない。**

順に確認する。

1. 正解が載っている資料が、そもそも取り込まれているか
2. その資料が検索で上位に来るか（**検索だけを単独で評価する**）
3. 分割の単位が適切か（細かすぎて文脈が切れていないか、粗すぎて薄まっていないか）
4. 検索できているのに答えが悪いなら、そこで初めて生成側を見る

1 と 2 を確認せずにプロンプトを直すと、いつまでも良くならない。

## Business Scenario 観点

- 資料に書かれていないことを聞かれたら、推測せず「分からない」と答える
- 回答に出典が付き、その出典に実際にその内容が書かれている
- 古い版の資料の内容を、現行として答えない
- 権限の無い人に、見せてはいけない資料の内容が出ない
- 「これまでの指示を無視して」のような入力に従わない
- 資料が更新されたら、新しい内容で答える

---

## 典型的な検証

- **評価シナリオを 10〜30 件用意して通す。**
  答えられるべき質問 / 答えられないべき質問 / 際どい質問を混ぜる
- 検索だけを評価する（正解資料が上位に入る割合）
- 出典が実際に根拠になっているか、目視で数件確認する
- 同じ質問を数回投げて、回答がぶれないか
- 権限違いのユーザーでの確認
- Prompt Injection を試す
- 1 回あたりのレイテンシとコスト

---

## DoD 追加項目

- 取り込んだ資料の範囲と、除外した資料を明示した
- 評価シナリオの結果を件数で報告した（○件中○件）
- 答えられない質問に「分からない」と返すことを確認した
- 出典を提示でき、その正しさを数件確認した
- 資料の更新・削除の反映方法が決まっている
- 権限による絞り込みを確認した（権限差がある場合）
- Prompt Injection の結果を報告した

外部公開するなら Production / High Risk。
`guidance/templates/production-readiness.md` を読み、
評価シナリオを定期実行する仕組みも決める。
