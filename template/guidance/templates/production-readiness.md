# Production Readiness

Production / High Risk に昇格したときに読む。

昇格の合図は多くの場合これ。

> 良さそうなので毎日自動で動かしたい。

このとき、動くものはすでにある。ここからは**壊れ方**を設計する。

---

## 昇格したことを利用者に伝える

黙って厳しくしない。何が増えるかを短く説明する。

> 本番自動実行へ進むため、ここから Production 扱いに切り替えます。
> 再実行時の安全性、失敗時の復旧、監視、実行コストを追加で確認します。

---

## 必ず答える 4 つの問い

実装を触る前に、この 4 つに答えられるか確認する。
答えられないものがあれば、そこが未設計箇所である。

### 1. 同じ入力を 2 回処理するとどうなるか

二重計上・重複行が出るなら、まだ本番に出せない。
→ MERGE / パーティション上書き / Auto Loader などで冪等にする。

### 2. 途中で失敗した後に再実行するとどうなるか

中途半端な状態が残り、再実行で悪化しないか。
→ どこからやり直せば正しい状態に戻るかを決めて、記録する。

### 3. 過去分をやり直すとどうなるか

対象期間だけを入れ替えられるか。全部作り直すしかないなら、その時間とコストを見積もる。

### 4. 部分的に成功した場合どう復旧するか

10 店舗中 3 店舗だけ失敗したとき、成功分を保ったまま残りを流せるか。
→ 「全部やり直し」でよいなら、それを決定として明記する。

---

## 優先順位

迷ったらこの順で判断する。

```text
Correctness → Reliability → Recoverability → Observability → Cost
```

正しくないものを速くしても意味がない。
コストは最後だが、無視はしない（特に LLM 呼び出しと大規模な再処理）。

## Databricks でやること

| 必要なこと | 使うもの |
|---|---|
| 定期実行・依存関係・リトライ | Lakeflow Jobs |
| 継続的な取り込みと品質チェック | Lakeflow Pipelines（expectations） |
| 失敗通知 | Job の通知設定 |
| デプロイと環境分離 | Databricks Asset Bundles |
| 権限 | Unity Catalog |
| モデルのバージョン管理 | Unity Catalog のモデル |

- 監視の仕組みを自作しない。Job のアラートと Pipeline の品質チェックで足りることが多い。
- Bundle は**このタイミングで**作る。開発中は不要。
- 開発用と本番用のデータを同じ場所に書かない。

## 確認する観点

### 実行

- スケジュール（頻度・時刻・タイムゾーン）
- 上流データが揃う前に動いてしまわないか
- 前回の実行が終わる前に次が始まったらどうなるか
- タイムアウトとリトライ回数

### 失敗

- 失敗したことを誰がどう知るか（**「ログを見れば分かる」は監視ではない**）
- 気づくまでにどれくらいかかってよいか
- 失敗が続いたときに止めるか、流し続けるか

### データ

- 上流のスキーマが変わったときに気づけるか（黙って NULL にしない）
- 件数が異常に少ない / 多いときに気づけるか
- 品質チェックに引っかかった行をどうするか（止める / 隔離する / 通す）

### 権限とデータ範囲

- 実行するユーザー / サービスプリンシパルの権限は最小か
- 本番データに開発から書き込めてしまわないか
- 機微データが出力に含まれていないか

### コスト

- 1 回あたりの実行時間と規模
- データ量が 10 倍になったときに破綻しないか
- LLM を使う場合、1 日あたりの呼び出し回数と概算コスト

### 引き継ぎ

- 担当者が変わっても、何をどう直せばよいか分かるか
- 手動で復旧する手順が書かれているか

## 本番前に実際にやる検証

読むだけで終わらせない。次は実行する。

- **同じ処理を 2 回連続で実行し、結果が変わらないこと**
- 途中で意図的に失敗させ、再実行で正しい状態に戻ること
- 過去 1 期間分の再処理
- 本番相当のデータ量での実行時間の測定
- 失敗通知が実際に届くこと（**設定しただけで終わらせない**）
- 権限を絞ったユーザーでの実行

実行できなかったものは、**未検証として明示する**。

---

## Production DoD

- [ ] 4 つの問いすべてに答えられる
- [ ] Idempotent であることを 2 回実行して確認した
- [ ] 失敗を検知できる（通知が届くことを確認済み）
- [ ] 復旧手順が `docs/project.md` に書かれている
- [ ] 監視対象が決まっている
- [ ] 実行時間とコストの目安を報告した
- [ ] 権限が最小になっている
- [ ] 開発と本番のデータが分離されている
- [ ] 未検証事項を明示した

ML なら再学習の頻度と精度劣化の検知、
AI Application なら評価シナリオの定期実行も決める。

## 報告

Production では、確認済みと未確認の区別が特に重要になる。

```text
状態
VERIFIED           ← 開発環境で確認できた
PRODUCTION-VERIFIED ← 本番で実際に動いたことを確認できた
```

**本番で動かす前に PRODUCTION-VERIFIED と書いてはならない。**
