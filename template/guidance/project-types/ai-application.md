# Project Type: AI Application

LLM Application / RAG / AI Agent / Chat / AI Function / Tool Calling / Agentic Workflow

AI Application は、動くデモを作るのが簡単で、信用できるものを作るのが難しい。
**それらしい嘘をつかないこと**が成果物の条件になる。

---

## 確認すべき観点

### 誰が何のために使うのか

> 誰がこれを使いますか？社内だけですか、お客様も使いますか？

外部に出るなら、その時点で Production / High Risk。

### 答えられなかったときにどうするか

必ず聞く。ここを決めないと、AI は常に何か答えてしまう。

> 情報が見つからないとき、「分かりません」と答えるのと、
> それらしい答えを出すのでは、どちらが困りますか？

業務利用ならほぼ確実に前者。**「分からない」と言える設計にする。**

### 間違えたときに何が起きるか

> この回答をそのまま信じて行動されると、まずいことはありますか？

金額・契約・医療・法務が絡むなら、根拠の提示と人間の確認を前提にする。

### 何を根拠に答えるのか（RAG の場合）

> どの資料に基づいて答えるべきですか？
> 古い版と新しい版が混ざっている資料はありますか？

版の混在は RAG の代表的な事故。取り込む前に決める。

### 見せてはいけない情報

> 人によって見せてよい情報が違いますか？

違う → 検索の時点で絞る。回答時にフィルタするのでは漏れる。

### 何ができたら成功か

> どんな質問に答えられれば「使える」と言えますか？

ここで出てきた質問がそのまま評価データになる。**必ず具体例を 5〜10 件もらう。**

---

## Databricks での作り方

| やること | 使うもの |
|---|---|
| モデル呼び出し | Foundation Model API / Model Serving |
| SQL からの LLM 利用 | AI Functions（`ai_query` など） |
| ベクトル検索 | Mosaic AI Vector Search |
| 実行トレース・評価 | MLflow Tracing / MLflow Evaluation |
| データ・権限 | Unity Catalog |
| 定期処理 | Lakeflow Jobs |

- 独自のベクトル DB を立てない。Vector Search がある。
- 独自の Agent フレームワークを書かない。
- トレースを自作ログにしない。MLflow Tracing がある。
- 一括分類・一括要約のようなバッチ処理は、Agent を作らず AI Functions で済むことが多い。
  **まず SQL 1 本で済まないか確認する。**

---

## モデルの選び方

- 最初から最大のモデルを選ばない。小さいモデルで評価してから上げる。
- 逆に、品質が出ないときにプロンプトだけで粘らない。モデルを上げて比較する。
- 判断は評価結果で行う。体感で決めない。

---

## RAG の要点

品質が出ないとき、**原因は検索側にあることが多い**。生成側を先に疑わない。

- 検索が正しい資料を持ってこられているか、まず**検索だけ**を評価する
- 分割の単位が細かすぎると文脈が切れ、粗すぎると無関係な情報が混ざる
- 元資料の更新をどう反映するか決める（決めないと古い答えを返し続ける）
- 回答には必ず出典を付ける。出典を確認できない回答は使えない

---

## 落とし穴

- 手元の質問 3 件で試して「動いた」とする
- 評価データを作らずにプロンプトを何度も直す（良くなったか分からない）
- 「分かりません」を返せず、必ず何か答えてしまう
- 利用者の入力をそのまま指示として扱う（Prompt Injection）
- 検索対象に権限外のデータが混ざっている
- 呼び出し回数とコストを見積もらないまま本番に出す

---

## 典型的な検証

- **評価シナリオを 10〜30 件作って通す。** 手動の思いつきテストで終わらせない
  - 答えられるべき質問
  - 答えられないべき質問（資料に無い、範囲外）
  - 際どい質問（似ているが違う、古い情報を聞く）
- 出典が実際に回答の根拠になっているか（それらしい出典を付けていないか）
- 同じ質問を数回投げて、回答が大きくぶれないか
- 権限の違うユーザーで、見えてはいけない情報が出ないか
- 「これまでの指示を無視して」のような入力に従わないか
- 1 回あたりのレイテンシとコスト

---

## DoD 追加項目

- 評価シナリオを作成し、結果を件数で報告した（○件中○件成功）
- 答えられない質問に対して「分からない」と応答することを確認した
- 出典・根拠を提示できる（RAG の場合）
- Prompt Injection を試し、結果を報告した
- 権限外データが出ないことを確認した（権限差がある場合）
- レイテンシとコストの目安を報告した

外部公開する場合は Production / High Risk として
`guidance/templates/production-readiness.md` も読む。
